# ADR 0005: Telegram Mini App surface, `initData` authentication, and API conventions

Status: Accepted
Date: 2026-10-10

## Context

The owner approved a Telegram Mini App for tasks and a read-only day/week
overview (improvement D7, [plan §7](../plans/improvements.md#7-phase-5--telegram-mini-app-d7-built-last);
layout in the [experience brief](../design/experience.md#telegram-mini-app)).
It must use the same operations as chat, add no sessions or new OAuth, keep
every query scoped to the user, and stay inside the free tier.

Telegram's Bot API reference (checked 2026-10-10,
<https://core.telegram.org/bots/webapps>) defines `Telegram.WebApp.initData`:
a query string signed with `HMAC-SHA256(data_check_string, HMAC-SHA256(bot_token,
"WebAppData"))`, where the data-check string is every field except `hash` and
`signature`, sorted, as `key=value` lines. It also states that **initData is
empty when the Mini App is launched from a keyboard button** (or inline mode).
Inline `web_app` buttons, the main Mini App, the menu button, and direct links
receive it.

## Decision

- **Surface.** The Worker serves `GET /app` (one HTML document, inline CSS,
  Telegram's script) and `GET /app/app.js` (a vanilla TypeScript bundle built by
  esbuild into `src/miniapp/generated/`, regenerated by `npm run check` and the
  Wrangler build). CSP allows scripts only from self and `telegram.org`; no
  framework.
- **Authentication.** Every `/app/api/*` request sends `Authorization: tma
  <initData>`. The Worker verifies the HMAC with constant-time comparison,
  rejects `auth_date` older than 1 hour (or more than 1 minute in the future),
  reads the Telegram user ID from the signed `user` field, requires it to be on
  the allowlist and to map to an active user, and answers `409
  setup_incomplete` until setup is done. Anything else is `401` with no data.
  No cookies, sessions, or stored tokens.
- **Reads** are `GET` endpoints scoped to the authenticated user. Events come
  from a live Google read with the synced copy as a labelled fallback, as
  `/weekly` does; events are read-only.
- **Writes** are `POST` endpoints that map one-to-one to chat task operations
  (the same functions build the D1 statements and deadline projections). Each
  carries the task `version` and a client-generated idempotency `key`; a
  replayed key returns the stored response; a version mismatch returns `409`
  with the current task. Cancelling (single or bulk) is a preview/confirm pair
  bound to a hash of the exact tasks and versions.
- **Keyboard entry point.** Because keyboard-button launches carry no
  `initData`, the persistent keyboard button is a plain **Open app** text
  button; the bot answers it with an inline `web_app` **Open app** button. The
  agenda, `/daily`, and `/tasks` carry inline `web_app` buttons; the main Mini
  App is configured in BotFather by the owner. The chat Menu button stays the
  command list.
- **Theme.** Telegram theme variables supply surfaces and text; the brand tide
  (`#0b6b62`) marks primary actions and today, overdue uses the theme's
  destructive colour, and status is always also written as text.

## Alternatives

- **A `web_app` keyboard button with a signed short-lived token in its URL.**
  One tap, but it adds a bearer credential to URLs (history, referrers, logs)
  and is a session in all but name. Rejected.
- **A cookie session after the first `initData` check.** Fewer HMAC checks, but
  adds session state, expiry, and CSRF handling. Rejected; verifying `initData`
  per request costs two HMACs.
- **Ed25519 third-party validation (`signature`).** Not needed: the Worker holds
  the bot token.
- **A frontend framework.** Unnecessary for six list screens; adds bundle size
  and a dependency.

## Consequences

- Opening from the persistent keyboard takes two taps; inline buttons and the
  main Mini App take one. The owner accepted this on 2026-10-10.
- `initData` older than an hour is refused, so an app left open for over an
  hour must be reopened (the app says so).
- Idempotency keys are stored per user for 7 days (`app_requests`).
- Each open costs a few Worker requests and bounded D1 reads; live Google reads
  are limited to the visible range. Measured in [capacity](../capacity.md)
  before release.
